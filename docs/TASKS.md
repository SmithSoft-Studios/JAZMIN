# JAZMIN backlog

Work is split into small, independently shippable tasks. Each task lists:

- its **acceptance test**: what must pass before it is done;
- whether it changes the **format**: if so, it needs an RFC update, usually a
  reader or writer feature, and new interop fixtures (see
  [CONTRIBUTING.md](CONTRIBUTING.md)).

Format 1.0 ([design note](design/format-1.0.md)) replaced the pre-release
drafts. Format numbers 1.1–1.3 below refer to those drafts.

Status: ✅ done · 🔶 partly done · 🔜 next · ⬜ later

## Performance (gaps found by the benchmarks)

| ID | Task | Acceptance | Format change |
|---|---|---|---|
| ✅ P-1 | **Paged sorted index**: sorted indexes are stored in ~64 KiB pages with a small directory (spec 8.1), so a lookup reads one page instead of decoding the whole index. 5M unique values: lookup 886 ms / 730 MB → 10.6 ms / 58 MB, 110 KB read | Single-id lookup on 10M rows reads < 64 KB of index; lookup time does not grow with row count | Yes (format 1.0) |
| 🔜 P-2 | Decode only the rows and columns needed from a chunk (skip-decoding) | `find` with `select` of 1 column is ≥ 2× faster than full decode | No |
| ✅ P-3 | **Columnar layout** (the only layout in format 1.0): delta, dictionary, bitmap and scaled-decimal encodings. Benchmark: deflate 3,497 → 1,292 KB, brotli 2,830 → 839 KB (gzipped JSON 3,338 KB) | `columnar.test.js`, `ColumnarTests`; RFC §5.4 | Yes (format 1.0) |
| ✅ P-12 | .NET direct typed decoding for the columnar layout (decode columns into typed arrays, then objects) | Typed deserialize of a columnar file as fast as a row file (≈50 ms on the benchmark) | No |
| ⬜ P-13 | Smaller indexes: delta-encoded postings in blocks, and no index for a column whose chunk statistics already locate values | Indexes ≤ 50% of their current size on the benchmark | Yes (minor) |
| ⬜ P-4 | Parallel chunk decompression for full scans (.NET `Parallel`, Node worker threads) | Full read ≥ 2× faster on 8 cores | No |
| 🔶 P-5 | Writer: build indexes faster. **Done:** trigram building without strings (JS 1,086 → 565 ms, .NET 420 → 323 ms); sorted index builder without a list per key or a lookup while keys arrive in order, entries kept off the large object heap (.NET), index pages compressed in parallel (.NET): on the benchmark a write with 3 indexes went from 164 to 94 ms (.NET) and 343 to 309 ms (JS), pages byte-for-byte unchanged. **Left:** .NET 2.2× and JS 1.8× a no-index write; the trigram index is the larger part | Write with 3 indexes within 1.5× of no-index write | No |
| ✅ P-10 | Parallel compression when writing (.NET and JS): compress chunks on worker threads and write them in order. Wide benchmark: .NET 11.3 s vs System.Text.Json 14.8 s; JS 66 s vs `JSON.stringify` 83 s (2 worker threads, synchronous API) | Wide write within 1.5× of System.Text.Json; same file contents | No |
| ✅ P-14 | Lower .NET read memory on wide files (done: reads 45–67 MB, open 0.03 s / 34 MB; statistics moved to per-column sections): reuse chunk buffers (ArrayPool), compact per-chunk statistics (1,938 chunks × 300 columns today), leaner columnar encoder | Wide reads under 300 MB peak; open under 0.3 s | Maybe (binary statistics) |
| 🔶 P-15 | Lower JS memory and time on wide files. **Done:** typed column buffers when writing, reused read buffers, inflate at the known size, rows built on demand, parallel compression (wide write 126.5 s / 493 MB → 66 s / 307 MB; sum of 3 columns 4.7 → 3.4 s; read every row 21.3 → 15.9 s). **Left:** write memory (307 MB vs 245 MB for `JSON.stringify`) | Wide write under 250 MB and faster than `JSON.stringify`; wide reads under 100 MB | No |
| ✅ P-11 | Direct decoding for full reads: chunk bytes straight into objects (.NET typed, JS rows), shared boxes and a short-string pool (.NET) | .NET deserialize 2× faster than System.Text.Json; JS full read faster than `JSON.parse` | No |
| ⬜ P-6 | Zstandard codec (id 3) where natively available | Interop fixture written by both sides | Yes (minor) |
