A file that asks for a code

remco.jzm holds the executives' pay for a remuneration committee. Its access key is an online key: on its own it doesn't open the file. Each time, it also needs an unlock token, which a key service gives out only after a code from the holder's authenticator app (Google Authenticator, Microsoft Authenticator and others). A copied key, or a copied file, opens nothing.

1 Start the sample key service

The service (dotnet/samples/Jazmin.KeyService, .NET 10) runs on this computer. It reads the file's unlock tokens from key-service/tokens.json, made with the file: it never holds the owner key, so it can't open the file itself. In a terminal, in the JAZMIN folder:

Allowing the origin null lets a page opened from disk call the service: only for a demo on your own computer.

2 Set up the authenticator

The file's owner gave this key to , and told the key service so. She sets up her authenticator once: scan the code with the app (or type the key), then enter the 6 digits it shows.

3 Open the file

Try the key alone first: the file refuses it and names what the key service needs (the file's id and the key's id). Then enter a fresh code from the app.

Each code works once, for about 30 seconds. Five wrong codes lock the key out for 5 minutes, then 10, 20 and so on.

The page keeps neither the code nor the token: open it again and it asks for a new code.

How it works

// When the file is written, the owner makes the key an online one:
grants: [{ key: thandi, rows: '*', columns: '*', mode: 'online', expiresIn: '30d' }]

// Opening it: the key alone isn't enough.
try { await JazminBrowser.open(bytes, { key }); }
catch (e) {   // JazminUnlockRequiredError: e.fileId, e.keyId
  const { token } = await post('/unlock', { fileId: e.fileId, keyId: e.keyId, code });   // after the 2FA check
  reader = await JazminBrowser.open(bytes, { key, unlockToken: token });
}

The key service checks, in this order: the code is right and hasn't been used; fewer than five wrong codes in a row; the key belongs to this person; the file has an online grant for it; the grant hasn't expired. Only then does it hand over the token. Stop the grant, or let it expire, and the key opens nothing, even on a copy of the file made earlier.

In production: sign people in with your own login instead of the demo's X-User-Id header, keep the tokens file encrypted, serve the service over HTTPS, and protect its admin endpoints. The service's README lists these.
